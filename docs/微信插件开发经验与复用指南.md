# 微信插件开发经验与复用指南

更新日期：2026-11-01（北京时间）  
经验来源：WeChatFnAlbum 0.1.x–0.4.0，Objective-C / Logos / UIKit / Theos。

本文供后续微信插件项目立项、实现、调试和交付时复用。重点是方法、真实失败原因和可查阅的代码，不要求新插件继续使用飞牛 NAS。文中的微信私有类与方法只代表本项目分析及测试过的接口，不能当作跨版本公开 SDK。

## 1. 先明确哪些经验经过验证

本项目的完整链路是：聊天中打开相册入口 → 选择 NAS → 登录、浏览和预览 → 下载素材到微信私有缓存 → 交给当前聊天的原生素材处理流程 → 微信上传 → 聊天中打开素材。

| 范围 | 截至本文的证据 | 后续项目应怎样使用 |
| --- | --- | --- |
| Dopamine、iPadOS 15.2、微信 8.0.75 | 安装加载及多轮用户真机验证 | 可作为本项目的基准环境 |
| 普通图片、GIF、实况照片 | 用户确认发送完成并能打开，GIF 动画和实况播放正常 | 可参考完整媒体适配链路 |
| 预览后切换“原图” | 0.1.1 后用户确认不闪退，原图发送与打开正常 | 可参考 Block 生命周期修复 |
| 日期条、AI 搜索、分类、人物头像 | 对应版本获得用户真机确认 | 可参考交互和分页实现 |
| 普通视频 | 0.3.3 用户确认未勾选原图时能发送并播放 | 不扩展为原视频、多视频和混选均已验证 |
| 加载遮罩与百分比 | 0.3.4 用户确认显示、预览正常 | 可参考进度与加载标识隔离 |
| 自动续期、内外网分流 | 有协议测试及部分实际使用反馈 | 实际长时间过期恢复、所有网络切换组合尚未逐项验收 |
| 视频预览音频、图片缩放 | 0.3.7、0.3.9 编译及模拟器检查通过，已部署 | 声音实际恢复、真实双指手感仍待用户确认 |
| 微信 8.0.76 | 参考 IPA 的静态分析 | 不能替代该版本的真机发送验证 |
| 全能签、修改 Bundle ID、免越狱注入 | 已调整宿主识别并输出注入包 | 不能由 rootless 安装成功推断签名注入成功 |

验收结论必须注明系统、微信版本、插件版本、安装方式和具体操作。编译通过、界面出现、消息进入聊天、上传完成、接收端能打开，是不同阶段。

## 2. 新项目先做最小纵向链路

先打通一个真实用户操作，再扩展功能。相册项目应先完成“一张普通图片从来源到接收端打开”，再增加 GIF、实况、视频、搜索与分类。其他插件也应选一个可独立验收的最小操作。

开始前记录以下信息：

- 目标微信版本及 build、iOS/iPadOS 版本、设备型号。
- 越狱安装还是签名注入，是否修改 Bundle ID，是否有其他插件。
- 入口、用户触发条件、成功结果、取消结果、失败时的原生回退。
- 需要哪些系统权限，宿主是否具备用途说明和签名权限。
- 哪些动作只是准备素材，哪个动作真正进入发送、上传等不可重复流程。

推荐的推进顺序：

1. 最小插件加载并留下自身版本诊断。
2. 验证目标方法存在、签名正确，入口可回退原生。
3. 加一个独立设置页与一个最小业务操作。
4. 用合成数据完成协议、生命周期和错误分支检查。
5. 真机验证完整结果，再扩展媒体类型或页面。
6. 分别验证 rootless 与签名注入，不混用结果。

## 3. 工程分层：Hook 越薄，后续越容易换版本

推荐结构：

```text
NewWeChatPlugin/
├── Tweak.xm                 # Hook、原生回退、初始化
├── Makefile
├── control
├── NewWeChatPlugin.plist    # 越狱加载器过滤范围
├── Sources/
│   ├── Host.*              # 主程序识别、扩展进程排除
│   ├── WeChatBridge.*      # 私有接口检查与调用、版本差异
│   ├── FeatureClient.*     # 网络、登录、业务协议
│   ├── FeatureController.* # UIKit 页面及交互
│   ├── Operation.*         # 异步状态、取消和交接
│   └── ReusableViews.*     # 加载层、缩放视图等
├── Resources/Plugin.bundle/
├── tests/                  # 合成数据、替身、设备开发自检
├── tools/                  # 包结构、架构、依赖检查
├── docs/                   # 架构、验证结果、开发经验
└── dist/                   # 当前版本交付物
```

不要把登录、列表、下载和所有微信私有调用都写进一个 Hook。新版本变化时，优先修改 Bridge，业务层保持独立。

本项目使用 `%config(generator=internal);`，让 Logos 生成基于 Objective-C runtime 的方法 Hook；发布检查另确认 dylib 没有 MobileSubstrate/ElleKit 的链接依赖。这不等于插件能自行加载：越狱环境依赖加载器，签名注入环境仍需主程序实际加载 dylib。[Theos Logos 说明](https://theos.dev/docs/logos-syntax)

## 4. 宿主识别与加载：不要只看 Bundle ID

本项目曾出现：同一 dylib 在越狱微信有入口，经全能签改 Bundle ID 后直接进入系统相册。原因之一是初始化只匹配原始 Bundle ID。

当前识别先看主 `.app`、`CFBundlePackageType=APPL`、`CFBundleExecutable=WeChat`，再检查实际私有接口；不在通知、分享等扩展进程初始化。该条件适用于当前目标，新项目遇到可执行名变化应重新核对。

必须区分两个层面：

| 层面 | 解决什么问题 | 本项目的处理 |
| --- | --- | --- |
| 加载器 Filter | 越狱加载器向哪些进程加载 dylib | 仍限定原微信 `com.tencent.xin` |
| 插件内部 Host 检查 | dylib 已加载后是否执行初始化 | 允许改 Bundle ID 的微信主程序，再验证接口 |

内部放宽 Bundle ID 不会自动放宽越狱 Filter，也不能修复“签名工具根本没注入加载命令”。

签名注入后没有入口，按以下顺序查：

1. 签名后的 IPA 是否真的包含新 dylib，是否误用了旧版本。
2. 微信主 Mach-O 的加载命令是否指向注入文件，路径是否可解析。
3. dylib 的架构、install name、依赖是否适合该环境。
4. 初始化是否执行，Host 检查是否通过。
5. 目标类、方法和 ABI 是否通过检查，是否因不兼容主动回退。
6. 最后检查其他插件是否改写了同一入口、Hook 链或加载顺序。

只看到文件存在，不能认定它已经加载。参考 IPA 用于分析入口、类和调用关系，不复制其中第三方插件，也不把多插件整合包当作干净对照环境。

## 5. 私有接口适配：类名相同不代表能安全调用

每次动态调用前，至少核对：类、selector、实例/类方法、参数数量、返回类型、参数编码。调用 `objc_msgSend` 时使用与真实方法一致的函数指针类型。

本项目典型接口：

| 接口/对象 | 本项目用途 | 必须注意 |
| --- | --- | --- |
| `ImageController -OpenMediaBrowser` | 聊天相册入口 | 仅在目标聊天上下文显示来源选择 |
| `didSelectMMAsset:finish:fromImagePicker:` | 图片、GIF、实况交接 | 不是普通视频的通用入口 |
| `MMAssetForLocalImage` | 本地图片适配基类 | 基类存在不代表上传回调完整 |
| `MMAssetForLocalVideo` | 本地视频适配基类 | 复制后路径、大小回调需要验证 |
| `CaptureVideoInfo` | 准备视频消息参数 | 不是直接塞进图片素材回调 |
| `CameraControllerDidTakeVideo:` | 当前聊天原生视频完成回调 | 发送前校验实际 delegate 与签名 |

方法签名里一个 Block 通常只显示为 `@?`，不能据此知道 Block 内部的参数。需要结合原生调用点、受控诊断和真实回调数据确认。

本项目纠正过的类型包括：图片大图回调第二参数是 `NSData *`，不是 EXIF 对象；视频文件大小异步回调接收 `NSNumber *`；实况视频相关回调返回 `NSURL *`。这些结论都要限定到已核对的接口与版本。

8.0.75 的实况大小 setter 出现 `q`，实现兼容已核对的 `q/Q`。这不是允许任意标量编码互换；`BOOL`、对象、整数及结构体要分别核对 ABI。

不兼容时不要猜地址、试参数或全局扩大 Hook 范围。保持原生入口，并在插件自己的设置/诊断中说明哪项检查失败。

分析新入口时，先从目标 IPA/可执行文件核对 Objective-C 元数据、selector 和调用点，再用开发构建诊断或受控的 Frida 附着确认真实对象、参数和完成回调。静态分析用于缩小范围，动态证据确认运行链路；接口名相近的旧开源插件只能作为线索。附着时记录 PID、插件版本和调用时间，应用重启后重新确认目标进程。

## 6. 真实调用链比“猜一个类”更重要

媒体流程至少拆成这些阶段：

```text
用户选择
  → 来源下载
  → 格式、字节和文件可读性检查
  → 本地素材对象
  → 微信请求原始数据/大图/视频参数
  → 原生素材完成回调
  → 微信异步上传
  → 聊天中发送完成
  → 打开并检查动画、声音或实况效果
```

失败时先确定停在哪个阶段，再改代码。不要将“已经交给微信”直接当作“已发送”。

本项目第一次图片卡住，并不是 NAS 下载失败：素材类能显示本地文件，但微信上传需要的原始数据、大图回调没有完成。补一个缩略图无法解决上传。

视频也曾进入图片大图处理回调而停住。最终调整为准备兼容 MP4、JPEG 封面及 `CaptureVideoInfo`，再调用当前聊天的原生视频完成接口。视频最终发送成功来自正确的交接链路，不是反复补齐图片占位图。

新项目应记录：入口 → 当前对象/delegate → 中间素材类型 → 回调 → 后续消费者。用一份合成素材确认每段，再接真实服务。

## 7. 异步回调、对象复制和状态机

### 7.1 跨异步边界必须明确持有 Block

“预览 → 切换原图”曾导致闪退。修复使用强类型 Block 属性和 `copy`，在原方法返回前持有微信传入的回调，并保持原生要求的调用顺序。

```objc
typedef void (^ImageCallback)(UIImage *image, NSData *data);

@interface ImageDelivery : NSObject
@property(nonatomic, copy) ImageCallback process;
@property(nonatomic, copy) ImageCallback result;
@end
```

不能只把回调当作不明类型 `id`，再假设任意保存和异步使用都安全。ARC 不能替代正确的类型、所有权和线程设计。

本项目大图链路需要先 Process、后 Result。若原始数据读取、解码或取消失败，也要结束相应流程，不能让消费者永久等待一个永远不会发生的成功回调。

### 7.2 测试“复制以后”的对象

微信可能复制素材对象。曾出现对象创建时本地路径正确，但继承的复制行为丢失路径，后续视频读取失败。

应核对复制后的：本地路径、原文件字节、时长、文件大小、封面、实况配对路径。不能只检查初始化结果。

本项目的自有不可变素材采用保留同一对象的复制策略，并处理返回值的所有权约定。此策略只适合确实可共享的不可变对象，不能直接用于带独立可变状态的新素材类。

### 7.3 每个异步操作有清晰的终点

推荐将操作建模为：准备中 → 可交接 → 已交接；旁路包括失败和取消。至少持有 `busy`、`cancelled`、`submitted` 或等价状态，防止双击、迟到回调和重复重试。

本项目使用三类互不替代的标识：

| 标识 | 隔离什么 | 何时变化 |
| --- | --- | --- |
| NAS `generation` | 账号、访问地址等会话身份 | 退出、换账号、切地址 |
| 页面 `generation` | 切图、换分类、重载列表后的旧结果 | 对应界面任务变化 |
| `loadingTicket` | 同一页面上不同加载层请求 | 每次开始/取消加载 |

同账号正常 token 续期不修改 NAS generation，避免把正常续期误判成账号切换。地址切换则需要变化，阻止旧请求继续发送。

## 8. 当前聊天校验：既防误发，也防误拦截

最初用 `chat.view.window != nil` 判断聊天是否还有效，导致全屏相册正常覆盖聊天时被误判“原聊天会话已改变”。底层聊天视图暂离窗口，不等于接收会话已经变化。

本项目保存打开选图流程时的聊天控制器、原 delegate 和接收会话标识；点击发送时记录当前 NAS 身份，下载完成交接前再次核对。

验证重点是：相册仍由原流程展示、当前聊天对象和接收者一致、delegate 未替换、导航状态仍指向原聊天、NAS 身份和代际未变化、操作未取消或提交。

所有素材及必要接口准备完成后才开始交接，减少先发一半再报错。进入微信回调后的多素材提交并不是可回滚事务；插件不能承诺已经发出的一部分可撤销，也不能在不确定状态下自动重发整批。

测试发送应由使用者在文件传输助手或明确的测试聊天触发。自动诊断可以检查素材和回调适配，不应顺带向聊天发送内容。

## 9. 媒体文件：检查内容，别相信扩展名

| 现象 | 实际证据/原因 | 可复用做法 |
| --- | --- | --- |
| MOV/MP4 报“无法打开” | 失败文件头是 JPEG，取到了封面 URL | 检查响应、文件头与资源字段，再判断编码 |
| 应用能读文件，AVFoundation 仍失败 | 某轮实验中默认 0600 与媒体服务读取失败相关 | 同时检查权限、保护属性和底层 AV 错误 |
| 改权限后仍打不开 | 实际资源字段错误尚未解决 | 每次修复必须用原失败素材复现验证 |
| GIF 变成静态图 | 重编码或素材类型识别丢失 | 保留原始 GIF 字节，验证最终动画 |
| 实况只发出静态封面 | 配对视频或原生适配不完整 | 检查两份资源与配对参数，不静默降级 |
| 网格加载慢、内存暴涨 | 把原视频当缩略图下载 | 网格仅请求缩略图，原文件按预览/发送下载 |

本项目普通视频优先使用 `additional.thumbnail.videoUrl`；`originalUrl` 实测可能是 JPEG 封面。这是飞牛协议细节，不是其他服务的通用字段规则。

本项目落盘素材显式设置 0644，并仍位于应用私有容器及原有文件保护范围内。不要把 0644 当作所有 AVFoundation 失败的通用修复，更不要递归放宽整个容器权限。

时长使用 NAS `mediaDuration`，本次 APK 的格式化链路证明单位是秒。新服务必须确认单位，不能凭数值大小猜秒或毫秒。

## 10. 缓存生命周期由消费者决定

预览文件与发送文件分开管理。预览关闭后可以取消并移除自己的临时文件；微信收到素材后可能还会异步读取，不能在选图页关闭时就删发送原文件。

本项目的约定：

- 每批发送创建独立目录，准备失败或取消时清理尚未交接的资源。
- 交接前写 `handoff.plist`，已交接目录不按固定时间自动删除。
- 设置页由用户确认发送完成后手动清理。
- 启动时只清理超过七天、没有交接标记的遗留项目，并非每次启动立即删除所有异常退出文件。
- 下载成功、内容可用及会话仍匹配后才把结果纳入可交接缓存；401 响应体不能当媒体落盘交接。

“已交接”只是文件保护标识，不证明微信已上传成功。未来如果加入自动清理，应先取得可靠的消费完成信号，再设计重试与清理规则。

## 11. 登录态、签名与网络切换

### 11.1 保存凭据不等于自动续期

本项目补齐了“保存凭据”之外的运行时续期链路。用户反复登录的具体触发原因仍应结合 NAS 的认证响应、凭据删除记录和网络状态判断，不能只凭现象认定 token 生命周期异常。

本项目会保存地址、账号、token、longToken、secret 到 Keychain，不保存密码。冷启动先尝试短令牌恢复，必要时用长令牌；HTTP 401 触发一次续期，成功后保存轮换凭据并重签原请求。

通用规则：

- 并发 401 合并为一次续期，其他请求等待结果。
- 重试保留原方法、查询和 HTTPBody 字节，只更新必要认证头和签名。
- 每个逻辑请求限制续期/重试次数，避免循环。
- 断网、服务忙、临时响应异常不能直接清除登录态。
- 明确认证失效或用户退出才清除；旧版本已删掉的凭据不能靠新代码凭空恢复。
- 换账号、退出和取消必须阻止旧续期结果重新激活会话。

这些是设计模式；新服务是否有 refresh token、令牌如何轮换，必须以其实际协议为准。本项目的 `longToken` 不应直接等同其他服务的 OAuth refresh token。

### 11.2 原始字节和实际 URL 是签名依据

协议还原应覆盖 URL 编码、中文、空格、加号、重复查询参数和 JSON 字节。不要计算一份 JSON 的签名，却重新序列化另一份 JSON 发出。

相对路径、绝对路径和重定向都要经过来源限制。本项目拒绝未配置媒体来源和重定向；配置了同一 NAS 的内外网别名后，只在显式可信地址之间重绑定 origin，保留路径与查询并重新签名。

### 11.3 Wi-Fi 名称有权限条件，未知不等于故障

注入 dylib 不会自动赋予宿主新的签名权限。`NEHotspotNetwork.fetchCurrent` 受 `wifi-info` entitlement 及系统规定的定位等条件限制；没有结果时不能断言一定是蜂窝网络。[Apple 官方说明](https://developer.apple.com/documentation/networkextension/nehotspotnetwork/fetchcurrent%28completionhandler%3A%29)

当前实现没有单独做蜂窝网络类型识别：它尝试读取 SSID，家中名称精确匹配走内网，其余情况（包括流量或无法读取名称）走外网。0.3.8 起自动回退不弹提示，主动检查权限的说明留在设置页；NAS 真实连接错误仍展示。

仅在打开新浏览页或保存配置时切换地址，发送过程中不自动更换。若以后需要严格区分蜂窝、Wi-Fi 和离线，应另加系统网络路径状态检测，而不是把 `SSID=nil` 当作完整网络分类。

## 12. UIKit 交互：先检查事件链，再重写控件

### 12.1 自定义控件可见却不能拖动

日期条问题涉及视图层级、装饰视图截获以及 UIControl tracking 方法名。正确签名是：

```objc
- (BOOL)beginTrackingWithTouch:(UITouch *)touch withEvent:(UIEvent *)event;
- (BOOL)continueTrackingWithTouch:(UITouch *)touch withEvent:(UIEvent *)event;
- (void)endTrackingWithTouch:(UITouch *)touch withEvent:(UIEvent *)event;
```

把浮层/滑块放在列表外，与 collection view 同级；装饰轨道关闭触摸；确认 hitTest 真正命中控件，并检查列表 pan 是否取消追踪。仅验证“value 改变后布局变了”不能证明真实 UIKit 事件能调用到实现。

### 12.2 输入框不弹键盘先做对照

本项目曾反复改搜索输入框，后来发现微信原生聊天输入框也不弹键盘，未连接实体键盘；重启系统键盘服务后两处一起恢复。

排查顺序：原生输入框是否正常 → 实体键盘及系统状态 → 第一响应者和窗口 → 弹窗呈现完成时机 → 插件布局和手势。只有插件异常时再聚焦自己的控件。不要把重启系统服务做成插件常规功能。

### 12.3 历史日期浏览需要双向游标

跳到旧日期后向上滑突然回最新，原因是“回到顶部”被当作全量刷新。历史范围应有独立头尾游标，上方插入较新数据时保留可见锚点；分页失败不提交游标。搜索按相关度排序时隐藏日期条，不把相关度列表硬映射到时间线。

### 12.4 图片缩放使用 UIScrollView

用 `UIScrollView + UIImageView` 承载原生 pinch、缩放和平移。初始适配并居中，放大时禁止父级左右切图，缩回后恢复；换图片和视口尺寸变化时重置。

改变视图层级后，要同步修正其他代码的 frame 坐标系及 `insertSubview:aboveSubview:`：视频/GIF 应对齐预览视口，不能继续使用已缩放图片的 frame 或把非同级图片当作 sibling。

### 12.5 进度显示真实值，结束要分阶段

本项目按当前逻辑下载的接收字节/总字节显示百分比；总量未知显示“加载中”，不伪造进度。下载完成后还有解码或播放器就绪阶段，不能一到 100% 就谎称显示完成。旧请求的回调不能隐藏新素材遮罩。

## 13. 音频会话是微信进程的共享状态

AVPlayer 能显示画面，不代表已建立正确的声音输出。应分别检查文件是否有可解码音轨、播放器 muted/volume、系统音量与输出设备，以及 AVAudioSession。

本项目 0.3.7 补齐 Playback / MoviePlayback 会话并激活。Playback 类别在静音开关打开时仍可播放媒体声音；系统音量及输出设备仍然生效。[Apple Playback 文档](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playback)

生命周期重点：

- 保存旧 category/mode/options，只在预览需要时接管。
- 切换、退出或应用失活，先暂停播放器，再结束自己的会话。
- 微信已切换到通话/录音等配置时，不用旧快照覆盖它。
- 激活失败回滚设置并给出错误，避免无声失败。

当前保护通过配置匹配判断是否仍由本插件持有，并不是系统提供的独占所有权锁，也不能精确恢复不可读的原活动状态。其他插件使用相同配置、通话中断和各种输出设备仍需专门真机覆盖。本文不把“补齐设置”写成用户已经确认恢复声音。

## 14. 两类交付物：deb 和 dylib 各有用途

| 产物 | 使用场景 | 要检查什么 |
| --- | --- | --- |
| rootless deb | Dopamine 等目标环境安装 | `/var/jb` 布局、包架构、实际依赖、加载 Filter |
| injection deb | 签名工具提取或识别插件包 | 工具是否支持包结构、提取后是否实际注入 |
| dylib + 资源 bundle | 签名工具直接注入 | 加载命令、路径、架构、系统权限和资源位置 |
| source.zip / manifest | 后续维护和核对 | 源码版本、构建信息、摘要和验证范围 |

本项目 rootless 产出 arm64 + arm64e；签名注入产出 arm64。arm64e 是本项目构建选择，不代表所有新插件或设备都应照抄该架构组合。

rootless 构建使用 `THEOS_PACKAGE_SCHEME=rootless`，相关安装前缀和链接处理以 Theos 方案为准，不靠手改压缩包里的目录模拟。[Theos Rootless 文档](https://theos.dev/docs/rootless)

资源路径以 dylib 实际所在目录定位最稳妥。本项目已包含 `dladdr` 后查找同级 `WeChatFnAlbum.bundle` 的代码，但当前只是解析 bundle，并未验证完整的外部图片/本地化加载功能。新插件增加资源时应实际使用该 bundle 取文件，并验证缺失回退。

不要依赖主 bundle 就能找到插件资源；也不要把 `/var/jb/...` 写死进需要免越狱注入的代码。插件设置放在微信内部，减少对系统设置扩展及额外运行库的依赖。

## 15. 诊断与验证要能解释失败

### 15.1 日志记录最小事实

建议字段：插件/宿主版本、类和 selector、类型编码、当前阶段、回调是否发生、回调参数类型、字节数、格式、错误 domain/code、取消及代际是否匹配。

不要记录密码、token、完整鉴权 URL、真实聊天内容或接收人。需要区分接收对象时优先记录相等性结果。本项目 `runtime.json` 记录接口，`send-checks.json` 记录条件布尔值；开发素材跟踪通过编译开关启用。

正式包应自动检查开发诊断未混入。不要只在源文件里写“调试专用”，还要检查最终 dylib。

### 15.2 失败定位表

| 现象 | 首先查 | 下一步证据 |
| --- | --- | --- |
| 插件入口完全没有 | 是否加载、Host、ABI 检查 | 新版本诊断、加载命令、Filter |
| 能浏览，发出后一直转圈 | 微信究竟请求了什么素材回调 | process/result、原始字节、大小对象、复制后路径 |
| 预览后操作闪退 | 崩溃栈、异步对象与 Block 所有权 | 确认实际 PC/异常和最近回调，不靠猜测改类型 |
| 文件无法打开 | 响应、文件头、权限、AV 错误 | 原失败文件是否真是媒体，是否取错封面 |
| 只有画面没有声音 | 音轨、静音、系统输出、音频会话 | 当前 category/mode 与实际音频路由 |
| 控件看得到但点不动 | hitTest、交互开关、方法签名、手势 | UIKit 实际调用的回调和父子关系 |
| 日期跳转后回最新 | 刷新入口和历史头游标 | 插入前后可见锚点、分页是否重建 |
| 经常重新登录 | 凭据有没有被删、续期是否执行 | 明确失效与暂时错误区分、并发续期日志 |
| 注入版独有失败 | 签名、加载路径、权限、包名 | 不用越狱成功结果替代其验证 |

外部运行时附着的 PID 会变。首次诊断没有记录到调用，应先确认附着的是新进程，必要时用开发构建内置的有限诊断；不能把“没采到回调”直接解释为“该方法从未调用”。

### 15.3 四层验证分别记录

1. **构建与包检查**：架构、install name、依赖、布局、资源、开发探针排除。
2. **独立原生/协议检查**：实际实现对合成 HTTP/WebSocket 服务、回调替身、取消和续期边界。
3. **模拟器 UIKit 检查**：布局、命中、系统回调、手势互斥、复用、键盘通知、迟到响应隔离。
4. **宿主真机验收**：微信内实际操作、发送完成、打开、动画/实况/声音效果、签名与多插件环境。

目前本项目原生测试有十组，曾扩展覆盖双地址切换；0.3.9 模拟器检查有 38 项。不同版本记录的数量不同，后续以实际脚本为准，不重复运行无关测试凑数量，也不把模拟器几何检查写成真实手指拖动验收。

## 19. 增量经验：流畅视频预览（0.4.0，2026-11-01）

大视频预览不必与发送共用完整下载流程。本次按用户后续选择，默认申请 NAS 的低清晰度转码流播放，勾选原图才完整下载原视频。不要把静态缩略图 URL 当作较小的视频，也不要在手机上先下载原片再压缩来声称减少首播等待。

NAS 转码通常有会话生命周期：申请、心跳、退出。需要处理切图/取消后迟到的申请结果，避免遗留服务器转码；控制请求沿用账号代际和续期约束。播放器的媒体分片使用独立网络栈时，要单独验证 Cookie、路径限制、证书、重定向及续期行为，不能把普通 API 客户端测试结果直接覆盖到播放器。

本项目用公开 AVURLAssetHTTPCookiesKey 配置转码路径内 Cookie；不把 token 放进播放 URL。API 心跳轮换凭据时重新配置 AVPlayerItem，恢复位置与播放/暂停状态。流畅模式显示缓冲状态，不能把非连续分片字节数当成整段下载百分比。转码不可用时由用户选择原视频，不自动大流量回退。

验证新增实际 AVPlayer + 合成 48 秒 HLS：确认原文件下载数为零、全部 HLS 分片尚未取完时已开始播放；之后切换原图并确认本地原文件播放和会话退出。协议/生命周期测试现为十组；原有 38 项 UIKit 检查仍通过。此证据不等于已验收真实 NAS 转码、iPadOS 15.2 长视频和内网穿透环境，仍需用户真机复测。

相关源码：`FNNASVideoPreview.m`、`FNClient.videoPlaybackConfiguration:error:`、`FNPreviewController.beginStreamPhoto:generation:ticket:`；实播测试为 `tests/test_stream_playback.py`。


### HLS 有声音但黑屏：验证轨道和分片，而非只验证时间前进

0.4.0 的合成 H.264 样本能播放，但真实 NAS 默认输出 HEVC + AAC / MPEG-TS，iPad AVPlayer 只识别声音，画面尺寸为零。应同时记录 tracks、presentationSize、readyForDisplay，并检查短分片的实际 codec/container。NAS 网页播放器在 decode/play 支持 videoEncoder、audioEncoder、channels，明确请求 h264/aac/2 后实际分片已切换 H.264。避免把网页播放器自身支持的转封装能力当成 AVPlayer 的能力。

流式加载百分比应使用首播目标缓冲时长作为分母，界面说明已缓冲秒数；不能把整段时长当成必须下载完的目标。原图大小直接来自媒体 fileSize，缺少元数据时显示未知，不用缩略流大小冒充原图大小。


### 视频启动慢先分段计时

真机 decode/info 约 18ms、decode/play 约 6 秒，说明优化信息请求缓存不能解决主要等待。应明确区分创建服务端转码、读 playlist、首分片、AVPlayer 首帧。对固定冷启动开销，少量提前申请和短期复用比重复创建任务有效；必须限制任务个数、有效期、后台清理、账号/地址 generation 和请求 single-flight，避免滚动列表触发整库转码。本项目 0.4.2 仅预热一个可见视频且不拉分片，20 秒到期关闭，未命中预热时仍需等待 NAS 冷启动。不要用进度动画冒充性能改进。


### 原视频渐进式播放替代服务端转码（0.4.3）

预热没有满足实际体验时，按用户选择撤销转码路线，先验证 NAS 原视频的 Range 请求。实际 113MB MP4 返回 206，64KiB 约 0.1 秒；AVPlayer 可按需读原文件，不要求文件先完整落地。使用真实 videoUrl 与精确路径、host-only Cookie，保持已有可信 NAS 地址规则。原图按钮只管理发送质量，不应让已经播放的预览重新开始。

测试要限制传输速度，并证明第一帧出现时实际发送字节少于文件大小；仅判断远程 URL 或播放器时间前进不够。还需检查非零画面尺寸、readyForDisplay、声音和原图切换。原视频播放失败后刷新媒体详情/凭据时，分配新的加载 ticket；首播成功已使旧 ticket 失效，复用旧 ticket 会导致重连后遮罩关不掉。无 Range 或不受支持的编码需明确提示，不能悄悄回到转码或全量下载。
